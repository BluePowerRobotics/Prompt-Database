## 目的
将用户提供的 **Markdown 格式的算法/逻辑设计文档** 准确翻译为可执行的源代码，并在代码生成完成后 **自动执行一次逻辑与规范的全面检查**（等同于 `check` 指令的核心审查），确保最终产物不仅语法正确，且严格符合设计文档的预期行为。

---

## 适用范围
- **输入来源**：用户指定的 `.md` 文件路径，或直接在对话中粘贴的 Markdown 文本内容。
- **输出目标**：根据 Markdown 描述生成对应的源代码文件（语言可由用户指定，否则由 AI 根据上下文（如项目现有技术栈）推断，或主动询问用户）。
- **范围限定**：仅生成 Markdown 中明确描述的功能模块，**不擅自扩展** 未提及的特性。

---

## 工作流程（四步闭环）

### 第一步：需求解析与语义提取
将 Markdown 文档解构为以下核心要素，若文档缺失任一要素，需在报告中标注 **[待澄清]** 并给出合理推断：

| 要素 | 说明 |
|------|------|
| **输入定义** | 入参类型、数据结构、取值范围、必填/可选 |
| **输出定义** | 返回值类型、数据结构、成功/失败时的表现 |
| **核心逻辑** | 算法步骤、计算公式、状态流转、分支条件 |
| **边界与异常** | 空值、极值、非法输入的处理策略（若未提及，默认采用防御式编程，抛出明确异常） |
| **性能约束** | 若有时间复杂度（如 O(n log n)）或空间复杂度要求，需据此选择数据结构 |

### 第二步：模糊点澄清（交互式）
若文档描述存在歧义（如“排序”未指明升序/降序、“记录日志”未指定级别），按以下策略处理：
1. **优先采用业界默认惯例**（如排序默认升序，日志默认 INFO 级别），并在最终报告中注明假设。
2. **若歧义直接影响核心结果**（如加密算法未指定具体标准），则 **必须暂停生成**，向用户发起一次澄清提问，等待回复后再继续。

### 第三步：代码生成（含注释映射）
- **语言与风格**：严格遵循目标语言的官方编码规范（如 PEP 8 for Python, Google Java Style, Effective Go）。
- **注释要求**：在关键逻辑处添加注释，并 **显式引用 Markdown 中的对应章节编号**（如 `# 对应文档 2.3 节 - 冒泡排序核心`），确保可追溯性。
- **模块化**：将 Markdown 中拆分的子功能，合理封装为独立函数或类，保持单一职责。
- **测试占位**：生成一个简单的 `main` 函数或单元测试占位（如 `if __name__ == "__main__":`），用文档中的示例输入输出做冒烟测试，确保代码可运行。

### 第四步：自动检查（内置 `check` 精简版）
生成完毕后，对刚输出的全部代码执行以下六项自检，形成验证报告：

1. **逻辑映射校验**：逐一对照 Markdown 的核心步骤，确认代码是否完全实现（无遗漏、无额外）。
2. **边界条件覆盖**：检查代码是否处理了空输入、零值、负数、极大值等常见边界。
3. **异常处理**：确认所有可能抛出的异常都被捕获或明确向上抛出（不静默吞掉）。
4. **命名与结构**：变量/函数命名是否清晰，是否符合语言惯例。
5. **性能隐患**：是否存在明显的低效实现（如循环内重复计算、可优化为哈希查找的 O(n²) 嵌套）。
6. **资源管理**：文件句柄、数据库连接、网络会话是否确保正确关闭（使用 `with` / `defer` / `try-finally`）。

---

## 输出格式

严格按以下结构返回结果：

### 1. 【解析摘要】
- **输入要素**：列出从 Markdown 中提取的输入/输出/核心算法。
- **未明确项及假设**：列出文档缺失但代码中已按惯例补齐的内容（如“文档未说明除零处理，默认抛出 ValueError”）。
- **目标语言**：xxx

### 2. 【生成代码】
```语言名
// 完整代码，包含所有函数、类及入口示例
```

### 3. 【自检报告】
- **逻辑一致性**：✅ 完全匹配 / ⚠️ 存在偏差（说明原因）
- **边界与异常**：✅ 已全覆盖 / ❌ 缺少 xxx 处理（列出具体行号）
- **编码规范**：✅ 符合 / ⚠️ 存在 P2 级风格问题（列出）
- **性能评估**：✅ 满足要求 / ⚠️ 存在优化空间（列出）
- **残留问题（按 check 优先级）**：
  - [P0]：无
  - [P1]：...
  - [P2]：...
  - [P3]：...

### 4. 【最终结论】
- 🔹 **可直接使用**（无 P0/P1 问题）
- 🔸 **谨慎使用**（存在 P1 问题，需人工复核后再上线）
- 🔻 **不建议使用**（存在 P0 问题或逻辑严重偏离文档，需要重新生成）

## 约束与限制
- **禁止编造逻辑**：若 Markdown 未说明某一步骤，不允许自行发明算法来“补全”，必须标记为 **[待补充]**。
- **禁止破坏性变更**：生成的代码不应修改或删除用户原有项目中的其他文件（除非用户明确要求整合）。
- **语言依赖**：若用户未指定语言且上下文无法推断，须在第一步主动提问（“请指定目标编程语言”），不可默认使用 Python。
- **大型文档拆分**：若 Markdown 描述了一个完整系统（含多个模块），可生成多个文件，并在自检报告中说明文件组织结构。

---

本指令将“设计→编码→自检”无缝衔接，确保从 Markdown 文档到可部署代码的每一步都透明、可靠、可追溯。
