# 代码规范检验 (Code Standard Check)

本 skill 用于对代码进行规范/接口检验，判定某段代码是否与当前项目依赖的权威参考保持一致，并输出结构化修正方案。检查内容包括参数定义，单位，正方向，采用坐标系等。

## 触发场景 (When to Invoke)

- 用户要求"检查这几行代码是否符合规范/是否符合官方写法"
- 用户要求"参照 xxx 校核代码"、"按官方示例检查"、"确认接口用法是否正确"
- 修改代码时想先确认某 API 的规范用法再动手

## 参照优先级 (Reference Priority)

调用本 skill 时，必须严格按照以下优先级选择参照来源，高优先级来源覆盖低优先级来源：

1. **官方示例**（最高）：FTC SDK 官方示例代码、框架（如 Road Runner / FtcRobotController）官方的 sample 与文档。
2. **md 文件**：项目内的设计/理论文档（如 `FTC_Format.md`）、README、说明文档。
3. **teamcode 代码**（最低）：本仓库已有的实现代码（如现有 Localizer / Filter）。

> 原则：当 md 文档与 teamcode 现有代码冲突时，以 md 文档为准；当官方示例与 md 文档冲突时，以官方示例为准。若三者皆无明确依据，则以该项目自身的约定为准，并在结论中标注"无权威依据"。

## 检验流程

### 1. 收集被检内容
- 明确待检验的文件路径、行号范围、方法/API 名称。
- 若仅给出行号或片段，先 `Read` 完整的相关上下文，避免断章取义。

### 2. 建立参照基线
按优先级依次查找参照来源，并记录每条依据的出处：
- 官方：搜索 SDK/sample 中对应的调用方式、接口签名、如 `readAccelerometer` / `initialize` / `setOrientation` 之类的约定写法。
- md：读取对应文档章节，提取公式、参数、边界条件。
- teamcode：读取同包或相关类的既有实现，作为风格与接口一致性的参考。

### 3. 对比与判定
逐项给出结论，每项标记 **PASS / WARN / FAIL**：

| 类别 | 检查要点举例 |
|---|---|
| API 签名 | 方法名、参数顺序、返回类型是否与参照一致 |
| 调用时序 | 是否先 init 再 read、是否有合理的状态保护 |
| 单位 / 坐标系 | 单位转换、坐标系映射、符号约定是否与参照一致 |
| 常量/参数 | 阈值、滤波参数、I2C 地址(如 0x19)是否与参照一致 |
| 命名与风格 | 命名、注释语言、结构组织是否符合项目约定 |

### 4. 输出修正方案
- 仅列出必须改动的项(FAIL)与建议改动的项(WARN)，PASS 项简要列出即可。
- 每条结论给出：问题描述 → 参照依据(文件/行号/章节) → 建议改动 → 影响评估。
- 改动时遵循"最少改动"原则，不添加需求之外的逻辑。

## 重要提醒

- 若发现被检代码是本次会话中新写的，可能与编辑历史中的接口不同步，优先用 `GetDiagnostics` 确认无编译错误，再结合参照给出判断。
- 涉及硬件的符号约定（如加速度计方向的 pitch/roll 符号）若无法从文档确定，标注"需实车标定"，不要臆断。
- 输出被检结论时，用文件链接引用参照出处，方便用户跳转核对。
